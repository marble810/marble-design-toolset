## Context

当前工作区入口通过单一的 `activeToolId` 驱动工具加载与渲染：路由层维护 `openToolIds`、`activeToolId` 和本地持久化，但真实挂载面只有一个活动工具实例。切换标签页时，路由会清空当前 `activeDefinition` 与组件引用，然后重新执行工具定义加载、技术栈预加载和组件懒加载流水线。这使当前标签栏更接近“导航器”而不是“会话容器”。

这与工作区实际使用场景不匹配。用户希望同时打开多个工具，并在它们之间来回切换而不丢失参数、预览缩放、导出注册和局部运行时状态。与此同时，工具体系中已经存在 `pixi`、`three` 等重型技术栈，简单地把所有标签页永久保活会引入新的资源问题，因此设计必须同时覆盖“保活”和“隐藏态生命周期”两个层面。

另一个约束是当前本地持久化语义已经基本满足“恢复上次打开的标签集合与活动标签”，且首次访问的默认状态本身就是空工作区。因此这次设计不应把问题扩大成“持久化所有工具内部状态”，而应聚焦在标签会话模型与运行时边界的纠正。

## Goals / Non-Goals

**Goals:**

- 让每个已打开工具在当前浏览器会话中对应一个稳定的、可重复激活的工具实例。
- 在标签切换时保留工具的内存状态、PreviewCanvas 导航状态和运行时注册结果。
- 只有关闭标签页时才销毁对应工具实例，并在重新打开时创建全新实例。
- 保留当前 `openToolIds` / `activeToolId` / `leftPanelWidthVw` 的本地持久化语义。
- 保留有效 URL hash 的深链能力，并明确“首次访问无 hash、无本地状态时显示空工作区”。
- 为工具提供可选的活动/隐藏生命周期读取方式，使重型工具可以在后台暂停资源消耗。

**Non-Goals:**

- 不在本次变更中持久化每个工具的内部参数、表单值或渲染状态到 localStorage。
- 不引入多窗口共享工作区状态、跨浏览器标签页同步或协同编辑能力。
- 不修改工具目录 schema、metadata 基础结构或技术栈声明机制。
- 不尝试一次性解决所有后台资源问题；本次仅提供统一生命周期信号与基础兼容路径。

## Decisions

### 1. 工作区从“单活动组件”改为“多会话保活栈”

路由层将不再只持有一个 `ActiveComponent` / `activeDefinition`。取而代之的是按 `toolId` 建立会话记录，并在 `openToolIds` 顺序上渲染一组稳定 keyed 的会话容器。每个会话在首次打开时懒加载一次，之后只在活动/隐藏之间切换可见性；当标签被关闭时，对应会话从集合中移除并触发卸载。

之所以选择保活实例，而不是在切换时序列化工具内部状态，是因为用户明确需要“真正的 tab”语义。序列化方案虽然可以保留部分表单值，但无法自然保留组件内部引用、导出注册、WebGL 上下文和预览导航状态，也会把大量恢复逻辑下放给每个工具。

备选方案：继续维持单活动组件，并要求每个工具实现序列化/恢复接口。否决原因是实现成本高、体验不一致，且仍不能覆盖复杂运行时对象。

### 2. 每个工具会话拥有独立的壳层上下文与导出上下文

当前 `tool-shell-context` 在路由层只注入一次，并由活动工具不断覆盖其中的 metadata 与 menu actions。该模型在“同一时间只有一个已挂载工具”时成立，但在多会话并存时会导致所有会话共享同一份 active-only 壳层上下文。

因此，工具会话需要被一个专用的 session wrapper 包裹，由 wrapper 为该会话单独注入 tool shell context，并继续复用 `ToolShell` 已经具备的每实例 canvas export registry。这样每个保活实例都拥有独立的 metadata、menu actions 和 export 注册表，不会因为活动标签变化而相互污染。

备选方案：继续沿用路由级单例 shell context，只在 DOM 层隐藏非活动会话。否决原因是上下文语义错误，后续调试和扩展成本高。

### 3. localStorage 继续只存工作区选择，不存工具内部快照

本次保留现有持久化结构：`openToolIds`、`activeToolId`、`leftPanelWidthVw`。刷新后，工作区只恢复打开了哪些标签以及哪个标签是当前活动标签；各工具的内部参数仍按工具默认值重新初始化，除非未来单独定义“工具状态持久化”能力。

这样做的原因是当前用户需求已经明确区分了两个层面：

- 需要恢复“上次打开了哪些 tabs”。
- 需要在不刷新页面的前提下，切换 tab 时保留当前实例状态。

把两者混为一个需求会显著扩大协议范围，并迫使所有工具实现可序列化状态模型。

### 4. 为工具提供可选的活动/隐藏生命周期信号

保活实例会让 Pixi、Three、动画和计时器型工具失去“切走即卸载”的天然资源回收路径。因此运行时需要提供一个统一的活动状态读取接口，让工具能在标签失活时暂停动画帧、观察器或高频计算，并在再次激活时恢复。

这个生命周期信号应当是可选消费的：现有工具即使不使用它，也必须继续兼容；而重型工具可以按需采用它，逐步把后台资源占用收敛到可接受范围。

备选方案：由框架强制冻结所有隐藏工具的副作用。否决原因是框架无法可靠识别每个工具的私有后台工作，也无法安全替代工具执行暂停/恢复逻辑。

### 5. 隐藏态采用“保留挂载、移出交互”的显示策略

非活动会话应继续保留在 DOM 与组件树中，但不参与当前工作区交互。推荐策略是使用会话栈容器，让活动会话可见，隐藏会话通过 `display: none` 或等效的非交互样式脱离当前视图，同时保留组件实例身份。

这样处理的原因是当前 PreviewCanvas 已经通过 `ResizeObserver` 和显式 viewport 重新测量来适应尺寸变化，手动缩放状态本身存储在组件内部。只要组件不被卸载，显示状态恢复时可以重新进入正常测量路径，而不需要额外序列化缩放和平移状态。

备选方案：将隐藏会话迁移到 detached DOM 或自定义缓存容器。否决原因是实现复杂度高，而现阶段没有证据表明简单保活栈不足以满足需求。

## Risks / Trade-offs

- [隐藏会话继续占用内存或 GPU 资源] → 通过可选活动/隐藏生命周期信号让重型工具主动暂停后台工作，并在后续实现中优先接入 Pixi / Three 类工具。
- [多会话并存使路由层装配逻辑更复杂] → 通过单独的 session wrapper 把“每个工具实例的上下文注入与加载逻辑”从页面 orchestrator 中拆出，避免在 `+page.svelte` 中堆积条件分支。
- [隐藏容器重新显示后，个别预览实现可能需要额外刷新] → 依赖现有 ResizeObserver 重新测量，同时为工具暴露活动恢复时机，必要时由工具在恢复时主动请求刷新。
- [用户误以为刷新后也会恢复工具内部参数] → 在 spec 与文档中明确区分“标签集合持久化”和“实例保活”是两个层面，本次仅覆盖前者加当前会话保活。

## Migration Plan

1. 保持现有 localStorage key 与数据结构不变，避免引入持久化迁移成本。
2. 先把工作区路由改造成会话栈模型，并让现有工具在不消费生命周期信号时仍能正常运行。
3. 对已知重型或有后台副作用的工具补充活动/隐藏生命周期消费逻辑。
4. 更新工作区规范与工具编写文档，明确“切 tab 不销毁，关 tab 才销毁”的新模型。

回滚策略：如果实现阶段出现不可接受的资源或兼容性问题，可以回退到单活动组件模式，因为本次不改变持久化 schema，不会留下额外的本地数据迁移负担。

## Open Questions

- 是否需要在后续变更中增加“每个工具内部状态持久化”的独立 capability，而不是继续依赖当前会话内保活。
- 是否需要为工作区设置一个最大保活标签数量上限，以控制低端设备上的资源占用。
- 活动/隐藏生命周期接口最终应该以 context、store，还是更轻量的 helper 形式暴露给工具作者。
