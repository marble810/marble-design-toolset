## Context

当前 PreviewCanvas 组件在结构上仅包含工具栏与可缩放视口（viewport）。工具若想在右侧面板补充状态字符、标识图标或轻量说明，只能自行在工具层做绝对定位，容易与共享缩放/平移交互耦合，且样式一致性较差。

本次变更目标是增加“外置于画布外”的信息块能力。这里的“外”定义为：信息块不覆盖在画布内容内部，而是锚定在 Canvas 框右侧下方，随画布平移与缩放后的框体位置同步更新。

约束来源：
- 仅允许 div、p、PixelIcon 三类元素。
- 首版容量限制为最多 5 行，信息块固定宽度 20em。
- 单行文本溢出使用省略号，hover 时显示全文 tooltip。
- 首行支持 IconOnly / IconAndTitle / TitleOnly 三种模式，后续行仅允许纯文本。
- 以上限制需要保留后续调整空间。
- 不影响既有 Fit、1:1、滚轮缩放、拖拽平移、中心锚点定位能力。

## Goals / Non-Goals

**Goals:**
- 在 PreviewCanvas 中提供统一的外置信息块挂载能力，位置贴合 Canvas 框右下锚点。
- 通过框架渲染协议约束可用元素，仅输出 div、p、PixelIcon。
- 提供 helper 驱动的开发者友好输入方式，降低工具作者拼接 DOM 的成本。
- 对行数与视觉宽度执行一致约束（默认 5 行、20em），并提供未来可扩展的参数组织方式。
- 保证外置信息块不参与 viewport 的缩放与平移，不影响预览导航交互。

**Non-Goals:**
- 不支持任意 HTML 节点注入。
- 不支持交互型控件（例如输入框、按钮、链接）放入信息块。
- 不在本次引入富文本排版（多列布局、自动换行策略定制、Markdown 渲染）。
- 不改变工具层是否使用 PreviewCanvas 的决策模型。

## Decisions

### 决策 1：信息块采用“画布外独立区域”，而非 viewport 内覆盖层
- 方案：在 PreviewCanvas 根节点中新增框架拥有的 footer/info 区域，视觉上位于内容区右下侧；该区域与 viewport 为兄弟层级。
- 原因：
  - 明确满足“canvas 外”的语义。
  - 避免被 transform 链路（pan/zoom）影响。
  - 降低与预览内容命中区域冲突的概率。
- 备选方案：在 viewport 内做绝对定位 overlay。
  - 放弃原因：虽然实现快，但语义上仍属于画布区域内部，且更容易与拖拽交互竞争。

### 决策 2：采用“结构化数据输入 + 框架统一渲染”，而非开放 snippet
- 方案：为 PreviewCanvas 提供 helper + 结构化输入模型。工具使用 helper 构造信息块数据，框架负责渲染为受限节点树（div/p/PixelIcon）。
- 原因：
  - 能硬约束元素白名单，不依赖工具作者自觉。
  - 便于统一做行数/字符数校验与降级处理。
  - 更利于后续升级（国际化、诊断警告、自动截断策略）。
- 备选方案：新增 `footer` snippet。
  - 放弃原因：无法可靠限制节点类型，约束可执行性差。

### 决策 3：限制策略“固定宽度 + 省略号 + 静默裁剪”
- 方案：将 `maxLines=5` 与 `fixedWidth=20em` 作为集中默认常量。渲染前执行归一化裁剪（超量行丢弃）；每行文本单行显示并采用省略号，hover 时显示全文 tooltip。
- 原因：
  - 满足首版稳定约束。
  - 未来调整只需修改集中常量与文档，不破坏调用端。
  - 运行时裁剪可避免异常输入导致布局失控。
- 备选方案：按字符数硬截断（例如 30 字）并在开发模式输出告警。
  - 放弃原因：视觉宽度不稳定，且用户已确认采用静默裁剪策略。

### 决策 4：信息块首行使用固定三模式，后续行仅文本
- 方案：首行仅允许 IconOnly、IconAndTitle、TitleOnly 三种模式；第 2-5 行均为文本行。
- 原因：
  - 统一视觉层级，突出首行身份信息。
  - 降低渲染分支复杂度。
  - 与“装饰/信息”定位一致，避免演变成自由布局容器。
- 备选方案：每行都允许图标与混排。
  - 放弃原因：信息层级混乱，且增加布局与可读性风险。

### 决策 5：信息块默认不可选且不抢占预览交互
- 方案：信息块容器默认 `user-select: none`，并保持非交互定位语义。
- 原因：
  - 与当前 PreviewCanvas 的不可选策略一致。
  - 避免误选文本影响拖拽体验。
- 备选方案：允许文本选择。
  - 放弃原因：与“装饰/信息”定位不一致，且会引入误操作。

### 决策 6：开发者友好性以“helper 优先 + 最小样板代码”为核心
- 方案：提供 text/icon/header/body helper，调用端以少量声明即可完成信息块构造。
- 原因：
  - 工具作者无需处理布局细节与约束逻辑。
  - 与框架一致性更高，减少样式分叉。
- 备选方案：仅提供原始对象结构，不提供推荐构造方式。
  - 放弃原因：学习成本更高、容易出现不一致写法。

## Risks / Trade-offs

- [风险] 数据驱动接口相比 snippet 灵活度较低。  
  → Mitigation: 在类型层预留可扩展字段（例如段落样式标记），后续按需演进。

- [风险] 增加外置信息块区域会挤占可视高度。  
  → Mitigation: 使用紧凑高度与自适应隐藏策略；无内容时不渲染该区域。

- [风险] tooltip 若仅依赖鼠标 hover，键盘用户可能无法获取全文。  
  → Mitigation: tooltip 同步支持 focus 可见路径，保证可达性。

- [风险] 若未来允许交互内容，当前非交互假设需重构。  
  → Mitigation: 在本次明确非目标，后续以独立 change 扩展。

## Migration Plan

1. 扩展 PreviewCanvas 的公开输入契约（新增外置信息块输入字段），保持旧调用完全兼容。
2. 在 PreviewCanvas 内实现信息块渲染与约束裁剪逻辑，默认无输入时不影响现有布局。
3. 更新工具作者文档，给出最小示例与约束说明。
4. 增加测试：
   - 位置语义（画布外右下）
  - 行数上限与 20em 宽度约束
  - 溢出省略号与 hover/focus 全文 tooltip
  - 首行三模式与正文纯文本约束
   - 元素白名单渲染
   - 对缩放/平移交互零回归
5. 如发现布局回归，可通过功能开关临时禁用信息块渲染路径并保留旧行为。

## Open Questions

- 首行三模式是否需要允许隐藏标题时的占位对齐策略（例如 icon-only 对齐）？
- tooltip 的呈现细节是否采用纯 CSS title/伪元素方案，还是采用统一组件封装？
- 后续若要支持可选主题（颜色/透明度），应作为框架统一 token 还是每行局部配置？
